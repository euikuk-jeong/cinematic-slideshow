# Cinematic Slideshow — 요구사항 / 설계 (신규 모바일 앱 프로젝트)

> LumisShow(NAS 서버 기반 웹앱)와는 별개의 독립 신규 프로젝트. grilling 스킬로 논의 진행 중(2026-08-07~). 확정되는 대로 이 문서 기준으로 별도 GitHub 리포를 신설한다.

## 프로젝트 목적

기능 자체보다 **프로세스 학습이 진짜 목적**이다.
- Android/iOS 마켓(Google Play / App Store) 앱 배포 프로세스를 실제로 겪어보고 이해한다.
- 인앱 광고(AdMob) 기반 수익모델의 연동·정책·심사 과정을 이해한다.

이 목적에 따라 기능 범위는 의도적으로 단순하게, 배포 프로세스는 실제 절차(계정 가입 → 테스트 트랙 → 프로덕션 심사)를 생략 없이 완주하는 쪽으로 설계 방향을 잡는다.

## 앱 개요

기기(스마트폰) 자체 갤러리의 사진 앨범(폴더)을 선택해, Ken Burns 효과(줌·팬)와 전환 효과를 적용한 슬라이드쇼로 감상하는 **로컬 전용** 앱. 서버/클라우드 연동 없음.

## 앱 이름

**Cinematic Slideshow**

### 선정 과정 (이력)

1. **기능 직관형(ASO 지향) 컨셉으로 방향 설정** — 감성형/브랜드형보다 스토어 검색 키워드에 직접 노출되는 쪽을 선택.
2. 1차 후보 5개 제시: `Ken Burns Slideshow`, `Photo Motion Slideshow`, `AlbumFlow`, `Gallery Motion Slideshow`, `PhotoDrift Slideshow`, `Slideshow Live Photos`.
   - `Ken Burns`는 실존 인물(다큐멘터리 감독)의 이름이라 앱 타이틀에 직접 사용 시 상표/인격권 리스크가 있어 배제(스토어 설명문 등 서술적 언급은 무방).
3. 사용자가 `Slideshow Live Photos`를 1차 선택 → 검토 결과 **"Live Photos"는 Apple 등록상표**(아이폰 카메라의 정지사진+짧은 동작/소리 캡처 기능 고유 명칭)라 그대로 사용 시 Google Play 상표권 신고 대상이 될 수 있어 **반려**. 대안으로 `Living Album Slideshow` 등 제시.
4. "Living"이 어색하다는 피드백 → "Slideshow"는 고정하고 동작 효과 뉘앙스만 바꾼 후보 재제시: `Slideshow Zoom & Pan`, `Dynamic Slideshow`, `Cinematic Slideshow`, `Slideshow Studio`, `Slideshow Effects`. (참고: `Motion Photo`도 Google/Samsung 카메라 기능 고유명이라 후보에서 제외.)
5. 사용자가 `Cinematic Slideshow` / `Slideshow Studio` 두 개로 압축 → 유사 앱 존재 여부를 웹 검색으로 확인. **두 이름 모두 정확히 일치하는 기존 앱 없음.** 단, 스토어의 "Slideshow Maker" 계열 앱 대부분은 **사진→영상(mp4) 변환/편집 도구**(MoShow, Scoompa, SlidePlus 등)라 우리 앱(기기 내 실시간 재생, 영상 추출 없음)과 카테고리가 다름 — 이는 오히려 스토어 설명문에서 차별화 포인트로 쓸 수 있음.
6. 사용자가 "Live 같은 자연스러운 느낌"을 원해 추가 후보 제시: `Live Slideshow`, `Vivid Slideshow`, `Slideshow Alive`, `Breathing Slideshow`, `Ambient Slideshow`. (`Live Slideshow`는 "Live Photos"와 단어 조합·어순이 달라 리스크가 낮다고 판단해 후보에 포함 — "Live Wallpaper"처럼 일반적으로 통용되는 조합이라는 논리.)
7. 최종적으로 `Live Slideshow` vs `Cinematic Slideshow` 두 개를 놓고 의견 요청 → **`Cinematic Slideshow` 추천 및 확정**. 근거:
   - 상표 리스크 완전 제로 (`Live`는 Apple 기능명과 개념적으로 겹칠 여지가 미세하게 남지만 `Cinematic`은 그런 연상 자체가 없음)
   - Ken Burns 효과는 원래 다큐멘터리/영화에서 정지사진을 "영화적으로" 보이게 하려고 고안된 기법이라 `Cinematic`이 기능을 의미적으로 더 정확히 설명
   - `Live/Motion` 계열 이름은 스토어에 이미 포화 상태라 차별화가 어려움; `Cinematic Slideshow`는 정확 일치 기존 앱이 없어 검색 노출에 유리
   - 리스크: `Cinematic`이 "video maker" 앱들의 흔한 마케팅 단어이기도 해 "영상으로 내보내기" 기능이 있다고 오해될 수 있음 → **스토어 설명문에 "영상 제작이 아니라 기기에서 바로 재생하는 뷰어"임을 명시**하는 것으로 대응하기로 함.
8. 이후 `LumisShow Mobile`도 잠깐 검토됐으나, LumisShow(NAS 서버 앱)와 기능적으로 완전 무관한 독립 프로젝트로 가기로 한 결정(Q1, Q8)과 충돌하고 브랜드 혼동·향후 진짜 NAS 컴패니언 앱과의 이름 선점 문제가 있어 반려 — **`Cinematic Slideshow`로 최종 재확정**.

## 기술 스택 / 개발 환경

- **React Native (Expo)**. 신규 프레임워크 학습 자체는 이번 프로젝트 범위 밖 — 진입장벽이 낮고 클라우드 빌드(EAS Build) 지원이 좋은 스택을 선택.
- **iOS 빌드**: 로컬 Mac 없음 → EAS Build 클라우드 빌드로만 진행.
- **배포 순서**: Android 우선 배포. iOS는 추후(계정·빌드 비용 별도 발생) — 단, 개발 시점부터 iOS 확장을 염두에 두고 Android 전용 네이티브 모듈 사용은 피한다.

## 수익 모델

- **v1 범위: 광고 전용.** IAP(광고 제거 등)는 배포 프로세스 1회 완주 후 v2 확장 과제로 보류 — AdMob 연동과 Play 결제(IAP) 두 프로세스를 동시에 진행하면 실패 시 원인 분리가 어려워지기 때문.
- **광고 형식: 배너만.** 전면(Interstitial)·보상형(Rewarded)은 제외.
  - 배너는 노출(impression) 기반 수익이 기본이고 클릭 시 추가 수익 — "배너=클릭시에만 수익"은 오해임을 확인.
  - 전면 광고는 전체화면 강제 노출이라 배너보다 eCPM이 높지만 빈도 제한·정책 이슈가 있어 이번 범위에서 제외.
- **광고 노출 위치**: 사진(앨범) 선택 화면 + 설정 화면에만. **슬라이드쇼 재생(전체화면) 중에는 광고 노출 안 함** — 감상 몰입도가 앱의 핵심 가치이므로 재생 화면은 광고 지면에서 제외.
- **타겟 사용자층**: 전연령 일반 앱(아동 전용/Families 프로그램 아님) — 맞춤형 광고 허용, COPPA 등 아동 대상 제약 없음.

## 로컬 데이터 구조

LumisShow 백엔드(`PHOTO_ROOT` + `app.db` SQLite)와 동일한 개념을 로컬로 치환한다.

- **사진/음악 원본 파일은 앱이 복사·소유하지 않는다.** OS 미디어 라이브러리(Android MediaStore / iOS Photos)에 있는 그대로 두고, 앱은 `expo-media-library`가 제공하는 **참조(asset ID/URI)만** 저장한다.
- **DB(SQLite, `expo-sqlite`)에는 메타데이터만 저장**:
  - 앨범 정의(선택한 기기 앨범의 참조 ID, 표시 이름)
  - 앨범별 슬라이드쇼 설정(전환 간격/순서/반복)
  - 배경음악 트랙 연결(기기 음악 파일 URI 또는 번들 음원 경로)
  - 앱 전역 설정
- **주의**: 사진 참조 ID(iOS `PHAsset.localIdentifier`, Android MediaStore content URI)는 앱 재설치·OS 업데이트로 무효화될 수 있음 — 구현 시 "참조 무효화 감지 후 재연결 안내" 처리 필요(LumisShow의 mtime 기반 캐시 무효화와 개념적으로 유사한 문제).

## 권한 처리 흐름

- **요청 권한**: `READ_MEDIA_IMAGES`(사진), `READ_MEDIA_AUDIO`(배경음악용 기기 음악, Android 13+ 세분화 권한). 앱은 뷰어이므로 쓰기 권한은 불필요.
- **Android 14+ "부분 접근" 모드**: 지원하지 않음 — 폴더(앨범) 단위 선택이 핵심 UX(아래 "사진 소스" 참고)라 부분 접근(선택한 사진만 노출)과 구조적으로 맞지 않음. 부분 접근 상태 감지 시 "전체 앨범 접근이 필요합니다" 안내 후 설정에서 전체 허용으로 전환하도록 유도.
- **요청 시점**: 앱 최초 실행 시가 아니라 **사용자가 "앨범 선택" 액션을 실행하는 시점**에 요청(온보딩 화면 분리 불필요 — 앱이 사실상 "선택→재생" 단일 플로우).
- **요청 전 설명(rationale) 화면**: 시스템 권한 팝업 전에 "왜 필요한지" 설명 화면을 앱이 먼저 노출 → 거부율 감소 + Play 심사 시 민감 권한 사용 맥락 확보.
- **거부 시 처리**: 차단 화면 + "설정으로 이동" 버튼(OS 앱 설정 딥링크). 앱이 포그라운드로 복귀할 때마다 권한 상태 재확인.

## 사진 소스 상세

Android에서 "앨범"은 OS가 별도 관리하는 큐레이션 개념이 아니라 **폴더(bucket) 자체**(`Camera`, `Download`, `Screenshots`, 앱별 폴더 등) — `expo-media-library`가 이 폴더들을 앨범 API로 노출한다. 즉 폴더 단위 선택(Q11/Q12/MVP 표)과 동일한 개념.

- 앱 내 커스텀 컬렉션(임의 사진 다중선택으로 별도 앨범 구성) 기능은 **v1 범위 밖**. "정리 안 된" 카메라 폴더도 최근 사진 슬라이드쇼로는 충분히 유용하다고 판단, 기능 확장은 실사용 피드백 이후(v2)로 미룸.
- iOS는 이 개념이 다름 — iOS Photos의 "앨범"은 폴더와 무관한 사용자 큐레이션 컬렉션(스마트앨범 포함)이라, iOS 착수 시 앨범 선택 UX를 다시 검토해야 함.

## 번들 기본 음원

- **소스**: Pixabay Music. LumisShow에서 이미 검토된 이력 있음(`doc/context/20260703_0649_배경음악저작권안내릴리즈.md`) — **Pixabay License: 상업적 사용 가능, 크레딧 불필요**라 번들 음원으로 사용하기에 조건이 가장 좋아 그대로 채택.
- **구성**: 5개 무드 카테고리, 각 1곡(총 5곡).
  1. 잔잔한(Ambient/Piano) — 일상·풍경
  2. 감성적인(Cinematic/Emotional) — 여행·추억
  3. 경쾌한(Upbeat) — 파티·아이들·이벤트
  4. 따뜻한/노스탤직(Warm/Acoustic) — 가족·오래된 사진
  5. 웅장한/감동적인(Epic/Inspiring) — 여행·모험·졸업·결혼 등 행사
- 실제 트랙 선정은 구현 단계에서 Pixabay Music에서 카테고리별로 검색해 확정.

## 화면 구성 / 네비게이션

**3화면 구조**로 확정(홈 화면 별도 없음 — 앱 진입 시 바로 앨범 목록):

1. **앨범 목록** — 진입 화면. 기기 폴더(앨범) 목록 표시 + 배너 광고. 권한 미획득 시 이 화면 위에서 인라인으로 설명(rationale)→시스템 권한 요청→(거부 시) 차단 화면 처리(권한 처리 흐름 절 참고). 앨범 탭 시 다음 화면으로 이동.
2. **앨범별 설정** — 전환 간격 슬라이더 / 순서(순차·랜덤) / 반복 여부 / 배경음악 선택(기기 파일 또는 번들 음원) + 배너 광고. 설정은 앨범 단위로 로컬 DB에 저장(로컬 데이터 구조 절 참고). "슬라이드쇼 시작" 버튼으로 재생 화면 진입.
3. **슬라이드쇼 재생(전체화면)** — 광고 없음. **웹 버전(`frontend/assets/js/pages/slideshow.js`) 수준의 컨트롤 제공**(이 앱의 핵심 경쟁력으로 판단):
   - 탭 시 툴바 노출(일시정지/재개, 이전/다음, 종료)
   - 스와이프로 수동 넘기기
   - 뒤로가기(제스처/버튼)로 종료 → 앨범별 설정 화면으로 복귀
   - **재생 중 Keep Awake 기본 적용**(옵션 없이 항상 화면 꺼짐 방지)

## 개발 마일스톤 (작업 순서 — 일정 없음, 개인 프로젝트로 여유될 때 진행)

목표 일정은 두지 않고 **의존관계 기준 순서**만 정함. 기능이 먼저, 광고·배포 인프라는 그다음(중간에 멈춰도 "쓸 수 있는 앱" 상태는 남도록).

**Phase 1 — 기반 구축**
1. 신규 GitHub 리포 생성 + Expo 프로젝트 초기화
2. 로컬 DB 스키마 구현(`expo-sqlite`: 앨범/설정/음악 테이블)
3. 권한 처리 흐름 구현(rationale 화면 → 시스템 요청 → 거부 시 설정 딥링크)

**Phase 2 — 핵심 기능**
4. 앨범 목록 화면(기기 폴더 조회)
5. 앨범별 설정 화면(전환간격/순서/반복/음악선택 UI + DB 저장)
6. 슬라이드쇼 재생 화면(Ken Burns + 전환효과 + 웹 수준 컨트롤 + Keep Awake)
7. 배경음악 연동(기기 음악 파일 + 번들 음원 5곡 실제 트랙 소싱·삽입)

**Phase 3 — 수익화**
8. AdMob 계정 생성 + 배너 광고 SDK 연동(앨범목록/설정 화면)
9. 개인정보처리방침 작성 + GitHub Pages 호스팅

**Phase 4 — 배포**
10. Google Play Console 신규 가입 + 앱 등록(패키지ID/콘텐츠등급/타겟연령)
11. 내부 테스트 트랙 배포·검증
12. 비공개(폐쇄) 테스트 트랙 운영(신규 계정 프로덕션 액세스 요건 충족)
13. 프로덕션 심사 제출 → 배포

## 배포 계획

- **Google Play Console**: 신규 가입 예정 ($25, 최초 1회).
- **배포 트랙**: 내부 테스트 → 비공개(폐쇄) 테스트 → 프로덕션. 신규 개발자 계정의 "프로덕션 액세스" 심사 요건(비공개 테스트 트랙 운영 이력 요구) 대응 목적.
- **Apple Developer Program**: iOS 착수 시점에 별도 가입 ($99/년) — 무료 계정으로는 TestFlight 베타조차 불가하므로 마켓 배포 프로세스를 실제로 겪으려면 필수.

## 개인정보처리방침

신규 리포 내 GitHub Pages(`docs/privacy-policy.html`)로 호스팅. Play Console 제출과 AdMob 계정 승인 둘 다 공개 URL의 개인정보처리방침을 요구함(광고 SDK가 광고 ID 등을 수집).
